pdf-inspector-py

Does this PDF need OCR?

Roughly half of all PDFs already carry a real text layer. Sending those through an OCR service is slow and expensive for no gain. This tells you which half you are holding — and it runs entirely in your browser.

    What the verdicts mean

    VerdictMeaning
    text_basedA real text layer covers the document. Extract it directly; skip OCR.
    scannedPage images with no text operators at all. OCR is the only option.
    image_basedSome text operators exist, but the content is carried by images or by glyphs drawn as vector paths.
    mixedText and image-backed pages coexist. The per-page OCR list tells you which are which.

    Why a page gets flagged

    ReasonWhat was detected
    scannedA full-page background image with little or no usable text drawn over it.
    no_textNothing extractable and no image either — an empty or unreadable page.
    vector_textGlyphs are drawn as paths, not shown as text. There is nothing to extract, however clean the page looks.
    suspected_garbled_textA text layer exists but will not decode to Unicode — typically Identity-H fonts with no ToUnicode CMap, or Type3 glyph bitmaps.

    Use it

    pip install git+https://github.com/lsmman/pdf-inspector-py
    from pdf_inspector import classify_pdf

result = classify_pdf("document.pdf")
result.pdf_type          # 'text_based'
result.confidence        # 1.0
result.pages_needing_ocr # [] — 0-indexed

    Or from the shell:

    detect-pdf document.pdf --json

    How it runs here

    The page loads Pyodide and installs the real package — the same wheel you would pip install. Your file is read into the browser's memory and never uploaded. That is possible because the port is pure Python: no compiled extension to build, so it runs wherever Python does, including here.

    The trade-off is speed. Upstream is Rust and classifies a document in tens of milliseconds; this is slower, and slower again under Pyodide. If you need the throughput and can install a compiled wheel, use upstream.
